# 一、基础设施（Infra）

## 1.1 `saas_bench/slot.py` — 容器就绪探测与端口布局加固

v1.0 的就绪判断只看 HTTP 状态码，导致"HTTP 200 但应用尚未真正可用"的假就绪频繁放行，
verify 随即对未初始化的应用断言而误判。v1.1 将探针能力扩展为：

- **`health_bad_markers`**：响应体中出现指定子串（如 `Internal Server Error`、`502 Bad Gateway`）即判未就绪；
- **`health_required_markers`**：响应体必须包含指定子串（如 Roundcube 页面须含 `Roundcube Webmail`）才算就绪；
- **`extra_health_paths`**：同一应用探测多个关键路径，任一不通即未就绪；
- **`compose_health_services`**：对 compose 部署的应用，逐个 inspect 子服务的 `healthy/running` 状态
  （如 OnlyOffice 的 mysql / elasticsearch / documentserver / community 四件套）。

此外：

- **启动时校验端口布局**：同一 slot 内若两个应用（含其暴露的数据库端口）索引冲突，直接抛错而非静默运行；
- compose 网段按 `crc32` 派生，避免并行 slot 之间子网冲突；
- 更彻底的容器 / 卷 / 网络清理与 compose 启动重试。

# 二、任务与验证脚本（Tasks / Verifiers）

按缺陷的**类型**归类。除特别标注外，均为纯 bug 修复，不改变评分语义。

## 2.1 系统性 verifier bug（跨多个任务的同类缺陷）

**A. 全量解码容错（106 个 verify 文件）**
`subprocess` 文本模式默认严格 UTF-8 解码，应用数据（邮件正文、病历字段等）中一个非 UTF-8 字节
就会让整个检查抛异常。为所有 `text=True` 的调用统一加 `errors="replace"`。

**B. OpenProject psql 认证（9 个 Software 文件）**
verify 以 root 身份 `docker exec` 跑 `psql -U openproject` 走 Unix socket peer 认证 →
`FATAL: Peer authentication failed`，异常被吞后所有查询静默返回空串、检查连坐全灭。
统一改为 `-h 127.0.0.1` + `PGPASSWORD=openproject`。

**C. Baserow API/SQL 访问（6 个文件）**
- JWT 认证头前缀写错：`Token {jwt}` → `JWT {jwt}`（token-auth 返回的是用户 JWT）；
- SQL 查询表名错误：`database_application` → `database_database`（Baserow 真实表名）；
- 字段列引用错误：`f.db_column` 不存在 → 改用 `field_{id}` 拼列名。

**D. BigCapital schema 大小写与命名（6 处，跨 4 个 Business 文件）**
BigCapital 的 MariaDB 为 `lower_case_table_names=0`，标识符全大写；多个 verify 猜错表/列名而抛异常：

| 任务 | 错误标识符 | 修正 |
|---|---|---|
| business_031 | `CONTACT_NORMAL_NAME`（列不存在） | 删除该 OR 子句 |
| business_031 | `PUBLISHED`（列不存在） | → `PUBLISHED_AT` |
| business_051 | `mj.STATUS`（列不存在） | → `PUBLISHED_AT`，判定改为"非空即已发布" |
| business_143 | `MANUAL_JOURNAL_ENTRIES`（表名缺复数 s） | → `MANUAL_JOURNALS_ENTRIES` |
| business_143 | `j.STATUS='published'` | → `PUBLISHED_AT IS NOT NULL` |
| business_065 | 小写 `accounts`/`account_normal`（均不存在） | → 大写表名 + 按 `ACCOUNT_TYPE` 推导借贷方向 |

**E. OnlyOffice 文档下载（4 个文件）**
verify 走 `/api/2.0/files/{id}/download` 拿不到文档内容 → 所有"文档内容"检查失败。
改为 `filehandler.ashx?action=download` + `asc_auth_key` cookie（旧接口保留兜底）。

**F. code-server workspace 路径（多个 Software 文件）**
硬编码 `/home/coder/project/`、裸 `/home/coder/<项目>` 等路径 → 实际项目在 `/home/coder/workspace/`。
统一改为 workspace 路径并保留候选路径兜底。

**G. SiYuan API 认证（media_066 / media_067）**
SiYuan 的查询 API 用 `Token {token}` 认证（非 JWT 体系）。这两处的 `Token` 前缀是正确的，
不应改动——记录于此以防后续误伤。

## 2.3 重建的 verifier（改变评分语义，需注意与 v1.0 分数不可直接对比）

以下 verifier 在 v1.0 中被截断（docstring 宣称的检查数远大于实际实现数），或硬编码了与 fixture 漂移的期望值。
v1.1 将其重建为**运行时计算 ground truth**，既堵住"schema 存在即满分"的漏洞，也避免 fixture 变化导致的误判：

- **software_012**（原 4/13 检查）：重建为 12 项——直接 grep 容器内 todo-api 源码提取路由，
  逐行比对 Method / Path / 源文件 / 行号 / Version / Status / Deprecation Date；
- **software_018**（原 2/14 检查）：重建为 5 项——现场扫描依赖文件计算漏洞命中集合（当前 fixture 为空集），
  要求行集合精确相等（伪造行失败、正确报告零命中通过），并删除与 fixture 不符的死代码；
- **software_023**：期望项目集合由硬编码改为运行时扫描 manifest 动态计算；
  过滤器检查同时接受 option-ID（Baserow 单选过滤实际存的是 option ID 而非标签）。

## 2.4 任务定义修复

- **software_005**：任务要求将 Metabase 连接到 Baserow 的 Postgres，但描述从未提供数据库连接参数
  （host / 端口 / 库名 / DB 账密），使该步骤无解。在描述中补齐：
  `host.docker.internal`、端口 = Baserow Web 端口 + 15、库 `baserow`、用户 `baserow` 及密码。
  （配合 1.2 中 metabase 的 `--add-host` 生效。）
